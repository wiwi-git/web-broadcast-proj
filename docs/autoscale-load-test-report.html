테스트 환경

API 서버와 변환 워커는 같은 이미지를 쓰지만 별도 Deployment로 띄우고, 각각 HPA를 붙였다. 세션·방송·댓글·후원·변환 대기열은 PostgreSQL에, 영상 파일은 모든 Pod가 함께 마운트하는 볼륨에 둔다. 서버 앞에는 LoadBalancer Service가 있어 localhost:8080으로 들어온 요청을 준비된 서버 Pod에 나눈다.

HPA의 CPU 사용률은 요청량 대비 비율이다. 서버의 369%는 Pod 하나가 평균 0.92코어(250m × 3.69)를 썼다는 뜻이고, 한도(1코어)에 거의 닿은 상태다. 워커의 399%는 2코어(500m × 3.99)로, 한도를 꽉 채웠다.

시나리오 1

API 서버: 로그인 반복 부하

무엇을 걸었나

k6(load-test/load.js)로 가상 사용자를 다음 순서로 늘렸다 줄였다.

0:00–0:30
가상 사용자 0명 → 30명으로 늘림
0:30–3:30
30명 유지
3:30–3:50
30명 → 0명으로 줄임

가상 사용자 한 명은 한 번 반복할 때마다 아래 요청을 보내고 0.5초 쉰다.

  1. 부하용: GET /api/auth/me(CSRF 토큰) → POST /api/auth/login → GET /api/broadcasts → GET /api/videos. 로그인은 비밀번호를 bcrypt로 검사해서 요청 하나에 CPU를 많이 쓴다. 그래서 적은 가상 사용자로도 서버 CPU를 목표 위로 올릴 수 있다.
  2. 상태 확인용: 테스트 시작 때(setup) 회원 하나를 가입시키고, 방송 하나와 그 방송의 댓글 하나를 만든다. 매 반복마다 그 회원의 세션 쿠키 하나로 /api/auth/me, 방송 조회, 댓글 목록을 조회해 결과가 같은지 본다.

상태 확인 요청은 어느 서버 Pod로 갈지 모르고, 새로 생긴 Pod나 곧 사라질 Pod로도 간다. 세션이나 데이터가 Pod 메모리에 있었다면 여기서 실패했을 것이다.

시나리오 2

변환 워커: 1080p 영상 업로드

무엇을 걸었나

ffmpeg로 만든 1920×1080, 30fps, 60초짜리 테스트 영상을 회원 하나가 POST /api/videos로 6번 연달아 올렸다(09:32:38에 업로드 끝). API 서버는 업로드를 저장하고 "처리 중"으로 DB에 남기기만 한다. 워커가 DB 대기열에서 하나씩 가져가 1080p·720p·480p HLS로 변환한다. 서버 부하(k6)는 걸지 않았다.

시행착오

위 결과는 세 번째 시도다. 앞의 두 번에서 다음 문제를 찾아 고쳤다.

증상원인조치
서버 Pod가 시작하자마자 계속 재시작Service 이름이 server라서 쿠버네티스가 SERVER_PORT=tcp://…를 넣었고, Spring이 이것을 포트 설정으로 읽었다enableServiceLinks: false
첫 시도에서 방송·댓글 확인이 0% 통과부하 스크립트가 방송 생성 응답에서 id를 잘못 읽어 /api/broadcasts/null을 조회했다. 서버 문제는 아니었다(로그인 유지는 같은 시도에서 6,050/6,051 통과)응답 경로를 broadcast.id로 고침
업로드한 영상이 모두 변환 실패 (ffmpeg 종료 코드 137)워커 메모리 한도 1GiB 중 JVM이 75%를 잡아, 1080p를 변환하는 ffmpeg가 메모리 부족으로 강제 종료됐다워커의 JVM 힙을 20%로, 메모리 한도를 2GiB로
Docker Desktop 전체가 멈춤 (CPU 800% 이상, kubectl 응답 없음)최대값을 서버 5개, 워커 4개로 잡고 두 부하를 동시에 걸었다. 늘어난 Pod들의 한도 합(CPU 약 13개, 메모리 약 15GB)이 Docker Desktop 자원(CPU 10개, 메모리 8GB)을 넘었다최대값을 서버 4개, 워커 2개로 줄여 한도 합이 자원 안에 들어오게 함. 두 부하를 따로 확인

첫 시도(최대 5개 설정)에서도 서버는 2 → 4 → 5개로 늘었다가 부하가 끝난 뒤 5 → 4 → 3 → 2개로 줄었다. 스케일 동작 자체는 처음부터 정상이었다.

한계

  • 노드가 하나다. Pod가 늘어도 같은 맥북의 CPU를 나눠 쓴다. 그래서 최대값이 자원 한도에 묶이고, 4개에서도 CPU 목표를 맞추지 못했다. 실제 클러스터라면 노드 자동 확장(Cluster Autoscaler 등)이 함께 필요하다.
  • 공유 볼륨은 단일 노드에서만 동작한다. 노드가 여러 대면 ReadWriteMany 볼륨이나 S3 같은 오브젝트 스토리지로 바꿔야 한다.
  • 반응이 1분쯤 늦다. metrics-server가 약 1분마다 CPU를 갱신하고, 줄일 때는 60초를 지켜본다. 짧게 치솟는 부하에는 늘어나기 전에 지나갈 수 있다.
  • 요청 분산은 연결 단위다. Service는 TCP 연결마다 Pod를 고른다. k6 가상 사용자는 연결을 유지하므로, 새로 생긴 Pod에는 새 연결부터 요청이 간다.
  • 라이브 송출은 부하를 걸지 않았다. MediaMTX는 WebRTC 연결을 직접 들고 있어 한 대로 두었다. 방송 상태(준비·방송 중·종료)는 DB에 있어 서버 Pod 수와 상관없이 유지된다.
