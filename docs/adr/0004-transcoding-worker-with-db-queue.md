# 영상 변환은 별도 워커가 DB 대기열에서 가져가 처리한다

ADR-0001에서는 변환을 API 서버 안의 스레드에서 돌렸다. 하지만 변환은 CPU를 많이 쓰는 작업이어서, 업로드가 몰리면 API 응답까지 느려진다. 또 서버를 여러 대로 늘리면 각 서버가 재시작할 때 처리 중인 Video를 모두 다시 대기열에 넣으므로, 같은 Video를 중복으로 변환하게 된다. 그래서 변환을 워커 프로세스로 떼어내고, 부하에 따라 워커 수만 늘리고 줄일 수 있게 한다.

워커는 API 서버와 같은 코드와 같은 이미지를 쓰고, `worker` 프로필로 웹 서버 없이 실행한다. 대기열은 따로 두지 않는다. 처리 중인 Video 행 자체가 대기열이다. 워커는 `FOR UPDATE SKIP LOCKED`로 아직 아무도 점유하지 않은 가장 오래된 Video를 하나 점유한다. 그래서 워커가 몇 대든 서로 다른 Video를 가져간다. 대안은 RabbitMQ나 SQS 같은 메시지 큐였다. 하지만 지금 규모에서는 운영할 시스템이 하나 더 느는 것에 비해 얻는 것이 적다. 이미 쓰는 PostgreSQL로 충분하다.

점유에는 기한(기본 60초)이 있다. 워커는 변환하는 동안 기한의 1/3마다 점유를 연장한다. 워커가 죽어서 연장하지 못하면, 기한이 지난 뒤 다른 워커가 처음부터 다시 변환한다. 워커가 정상적으로 종료할 때는 점유를 바로 풀어서, 다른 워커가 기한을 기다리지 않게 한다. 결과 기록은 점유 토큰이 맞을 때만 성공한다. 그래서 점유를 잃은 워커가 늦게 끝나더라도 상태를 덮어쓰지 않는다.

## Consequences

- 업로드 직후 변환이 시작되기까지 최대 폴링 간격(기본 1초)만큼 늦어질 수 있다.
- 개발 환경에서 `./gradlew bootRun`으로 서버 하나만 띄우면 그 서버가 워커 역할도 같이 한다(`video.worker.enabled` 기본값 true). compose 배포에서는 API 서버가 `VIDEO_WORKER_ENABLED=false`로 변환을 넘긴다.
- 워커와 API 서버는 같은 저장소를 봐야 한다. 지금은 compose의 `media-data` 볼륨을 나눠 쓴다. 그래서 같은 호스트 안에서만 늘릴 수 있다. 여러 호스트(클라우드 오토스케일링)로 가려면 저장소를 S3 같은 객체 저장소로 바꿔야 한다. `VideoStorage` 인터페이스가 그 경계다.
- 워커가 죽으면 그 Video는 점유 기한만큼 늦게 다시 시작된다.
- Broadcast 동기화 같은 주기 작업은 API 서버에서만 돈다. API 서버를 여러 대로 늘릴 때는 주기 작업이 중복 실행되는 문제를 따로 다뤄야 한다.
