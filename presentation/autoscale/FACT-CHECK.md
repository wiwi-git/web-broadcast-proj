## 확인된 내용

- API·워커가 같은 이미지 사용, 워커는 웹 서버 없이 실행: `k8s/app/server.yaml`, `worker.yaml`, `application-worker.properties`.
- API는 변환 직접 실행 없이 PROCESSING 행 저장: `VideoService.java`. 단, 파일 저장 외에 ffprobe 검사도 한다.
- DB 행 대기열, `FOR UPDATE SKIP LOCKED`, 토큰 조건부 DB 상태 갱신, 기본 lease 60초·갱신 20초: `VideoJobs.java`, `VideoWorker.java`, `VideoWorkerProperties.java`. “1초마다 조회”는 유휴 시 폴링 간격이며 작업 중에는 순차 처리한다.
- 세션 JDBC·PostgreSQL·공유 PVC 사용, API readiness probe: application 설정 및 `k8s/app/`.
- 방송 상태 저장은 낙관적 락 충돌 처리: `BroadcastSync.java`. 주기 작업 전체의 중복 실행이나 외부 호출까지 한 번만 실행한다는 뜻은 아니다.
- API HPA 2~4, 목표 60%; 워커 1~2, 목표 70%: `k8s/app/autoscaling.yaml`.
- API 확장 2→3→4→3→2, 최고 CPU 지표 369%: `load-test/results/server-scale.txt`.
- 상태 check 16,719회 전부 성공, HTTP 실패 지표 0/39,015: `load-test/results/k6-server.txt`. 세 종류의 check 합계이며 사용자 16,719명이라는 뜻은 아니다.
- 워커 확장 1→2→1, 같은 구간 API CPU 2~4%: `load-test/results/worker-scale.txt`.
- 영상 6개 모두 공개·작업 분배는 보고서에 서술되어 있으나, 현재 저장된 원시 결과 파일에는 영상별 완료·점유 로그가 없다. 보고서 기록과 일치하는 수준으로 판정한다.
- CPU 백분율은 머신 전체나 CPU 한도 대비가 아니라 requests 대비다. 서버 369%는 250m의 3.69배, 워커 399%는 500m의 3.99배다. 9번 화면에는 이 기준이 표시된다. 나레이션도 “CPU 요청량 대비”를 넣으면 명확하다.

## 추가 주의점

1. “모든 상태가 서버 밖”은 세션·업무 데이터·영상 파일이라는 범위로 한정하는 편이 정확하다. MediaMTX의 실시간 연결 등 플랫폼 전체의 모든 상태를 외부화한 것은 아니다.
2. 점유 토큰은 **DB 상태 기록**을 보호한다. `VideoProcessor`는 토큰 검증 전에 파일을 공개하고 작업 디렉터리도 영상 ID별로 공유한다. lease 상실과 재점유가 겹치는 모든 상황에서 파일까지 중복 처리·덮어쓰기 없이 안전하다고 확대 해석하면 안 된다.
3. 단일 노드에서 목표 CPU 미달성 원인을 노드 자원 하나로 확정할 자료는 부족하다. 최대 Pod 수 제한과 bcrypt 중심 부하도 함께 고려해야 한다. “4개 상한에서도 목표 사용률을 넘었습니다”는 기록으로 확인된다.
4. `script.md` 목표 약 6분, README 약 7분 43초, timeline 461.795초(약 7분 42초)로 길이 안내가 다르다. 내용상 중대한 오류는 아니지만 목표 길이를 정리할 수 있다.

원본 영상·대본·장면은 수정하지 않았다.
