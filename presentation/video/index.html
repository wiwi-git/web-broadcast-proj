Web Broadcast는
휴대폰 카메라로 라이브 방송을 하고,
녹화한 동영상을 올리고,
누구나 시청할 수 있는 웹 방송 플랫폼입니다.
오늘은 방송자와 시청자, 두 사용자의 시점으로 화면과 기능,
그리고 그 뒤에서 동작하는 API와
기술을 차례로 보여드리겠습니다.
전체 구조입니다.
웹은 React와 Vite로,
서버는 Spring Boot 4와 Java 25로
만들었고, 데이터는 PostgreSQL에 저장합니다.
라이브 영상은 스프링이 직접 받지 않습니다.
미디어 서버인 MediaMTX가 영상을 받아 시청용 스트림으로
바꾸고, 스프링은 송출 허가와 방송 상태만 관리합니다.
업로드한 동영상은 서버 안에서 ffmpeg로 화질별 HLS로
변환하고, 후원 결제는
토스페이먼츠 테스트 모드로 연동했습니다.
먼저 방송자 시점입니다.
방송을 시작하려면 로그인해야 합니다.
로그인 상태는 JWT 대신, 서버 세션으로 유지합니다.
세션은 Spring Session JDBC로
데이터베이스에 저장해서
서버를 재시작해도 로그인이 풀리지 않고,
로그아웃도 즉시 반영됩니다.
쿠키를 쓰는 만큼, 웹에서 상태를 바꾸는 요청에는
CSRF 토큰을 헤더로 함께 보내도록 했습니다.
제목을 적고 방송 시작을 누르면,
서버는 준비 상태의 방송을 만들고 방송 키를 발급합니다.
한 사람이 동시에 진행할 수 있는 방송은 하나뿐이라,
이미 진행 중인 방송이 있으면 409와
함께 그 방송의 아이디를 돌려줍니다.
방송 키는 SecureRandom으로
만든 32바이트 값입니다.
발급할 때만 원문을 돌려주고,
데이터베이스에는 해시만 저장합니다.
방송 화면에서는 브라우저가 카메라와 마이크를 열고,
WebRTC 표준 송출 방식인 WHIP으로
미디어 서버에 영상을 보냅니다.
이 프로젝트는 WHIP 영상 송출
코덱을 H.264로 고정했습니다.
방송 생성에는 로그인 세션을 쓰고,
미디어 서버의 송출 허가에는 방송 키를 씁니다.
미디어 서버가 인증 훅으로 스프링에 묻고,
스프링이 키의 해시를 비교해서 허가 여부를 답합니다.
방송 상태는 스프링이 2초 간격으로 미디어 서버에 실제 송출
현황을 묻고, 조회에 성공하면 그 결과를 DB에 반영합니다.
이벤트 훅 대신 주기적 조회를 고른 이유는,
어느 한쪽이 재시작되어 이벤트를
놓쳐도 다음 조회에서 DB의 방송
상태가 저절로 맞춰지기 때문입니다.
동기화 도중 소유자가 방송을 종료하면
낙관적 락으로 충돌을 감지해 다음 주기로
넘기고, 이미 종료된 방송으로 송출이
계속 들어오면 서버가 연결을 끊습니다.
방송자는 라이브뿐 아니라 녹화한 동영상도 올릴 수 있습니다.
이때는 콘텐츠의 소유자가 됩니다.
업로드가 끝나면 동영상은 처리 중 상태가
되고, 서버 안의 단일 스레드
대기열이 ffmpeg로 원본 해상도에
맞는 화질의 HLS를 한 번에 만듭니다.
1080p 원본이라면 1080p, 720p,
480p 세 가지이고, 썸네일은 따로 추출합니다.
변환이 끝나면 공개 상태가 되어 바로 재생할 수 있습니다.
지금 규모에서는 메시지 큐가
과하다고 판단해 서버 안에 두었고,
변환 로직은 인터페이스 뒤에 두어 나중에
별도 워커로 분리할 수 있게 했습니다.
서버가 변환 도중 꺼지면, 다시 켜질 때
처리 중이던 동영상을 대기열에 다시 넣습니다.
이제 시청자 시점입니다.
시청은 로그인 없이 누구나 할 수 있습니다.
라이브 목록은 방송 중인 방송과 최근 종료된 방송을
나눠서 보여주고, 준비 상태의 방송은 보이지 않습니다.
방송을 누르면 미디어 서버가 만든 저지연
HLS를 hls.js로 재생합니다.
미디어 서버는 종료된 방송의 시청 요청을 인증 훅에서
거부하고, 웹은 방송 중일 때만 플레이어를 엽니다.
동영상 목록에는 변환이 끝난 공개
상태의 동영상만 최신순으로 나옵니다.
재생은 네트워크 상황에 따라 화질이
자동으로 바뀌는 적응형 HLS이고,
시청자가 원하는 화질을 직접 고를 수도 있습니다.
로그인한 회원은 댓글을 남길 수 있고,
댓글은 작성자만 수정하거나 삭제할 수 있습니다.
콘텐츠의 소유자라도 남의 댓글을
직접 수정하거나 지울 수는 없습니다.
버튼을 숨기는 건 화면의 편의일 뿐이고,
모든 권한은 서버가 검사합니다.
동영상 댓글의 더 보기는 마지막으로
본 댓글보다 오래된 댓글을 불러오는
커서 방식이라, 새 댓글이 달려도
기존 페이지 경계가 밀리지 않습니다.
시청자는 방송 중인 방송자에게 후원할 수 있습니다.
금액은 1,000원부터 50만 원까지 1,000원 단위이고,
자기 방송에는 후원할 수 없습니다.
후원하기를 누르면 서버가
먼저 결제 대기 상태의 후원을 만들고,
그 아이디를 주문번호로 토스페이먼츠 결제창을 엽니다.
결제 인증을 마치고 돌아오면, 서버는 결제 금액이
처음 저장한 후원 금액과 같은지 먼저 확인합니다.
승인을 요청하기 전에 금액이 다르면 실패로 끝내고,
이미 승인을 요청한 뒤라면 거절만 하고 결제 대기로 둡니다.
금액이 맞으면 토스페이먼츠 승인 API를 부르는데,
이때 주문번호로 만든 멱등키를 함께 보냅니다.
타임아웃으로 결과를 받지 못하면 결제 대기로 남겨 두고,
같은 승인 요청을 다시 보내면 같은
멱등키를 써서 승인이 중복되지 않습니다.
30분이 지난 결제 대기는 1분마다
도는 정리 작업이 처리합니다.
승인을 요청하기 전이면 만료시키고, 승인을 요청했다면
주문번호로 토스페이먼츠에 조회해서 결과를 맞춥니다.
여기서는 완료 처리한 샘플 후원으로,
시청자 화면의 후원 기록과 방송자 화면의 알림을 보여드립니다.
방송 중에는 완료된 후원을
3초 주기로 조회해서 알림을 띄웁니다.
공개되는 건 완료된 후원뿐이고, 실패하거나 취소된 후원은
후원자 본인만 후원 내역에서 볼 수 있습니다.
정리하면, 이 프로젝트에서 가장 신경
쓴 부분은 책임을 나누는 일이었습니다.
미디어는 미디어 서버에 맡기고, 스프링은
권한과 상태라는 비즈니스 규칙에 집중했습니다.
그리고 실패를 전제로 설계했습니다.
이벤트를 놓쳐도 맞춰지는 상태 동기화,
결과를 받지 못해도 다시 맞출 수
있는 결제 승인이 그 예입니다.
권한과 결제 흐름은 Testcontainers로
실제 PostgreSQL을 띄워 HTTP 요청
단위로 검증했고, 결제는 가짜 결제 서비스로 승인,
거절, 결과 모름을 모두 확인했습니다.
지금까지 Web Broadcast였습니다.
감사합니다.
